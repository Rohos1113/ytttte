## 1. Контракт API таблиц (согласован, менять нельзя)

```
GET /api/projects/{project_id}/node-llm/{node_key}/table?doc=<doc_id>&full=1
```

- `doc` — необязательный id документа из `.../documents`. Если задан — нормализуется только он.
  Если не задан — берутся все документы ноды, самый крупный JSON-документ считается основным,
  таблицы остальных документов добавляются в тот же ответ с префиксом источника в `id`.
- `full=1` — необязательный: вернуть длинные значения (`long_text`) целиком, без обрезки до 2000 символов.
- Контракт документа — существующий: `GET /api/projects/{id}/node-llm/{node_key}/documents`.

Пример выше — иллюстрация формы, значения `rows` урезаны. Полный ответ по `shots.json` содержит
колонку `ops.fields.кадры` (или отдельную таблицу кадров — см. 3.5/4.2).

### 1.2. Поля

| Поле | Тип | Смысл |
|---|---|---|
| `nodeKey` | str | ключ ноды, как в `canvas_graph` |
| `nodeType` | str | тип ноды (`plan`, `script`, `excel_gpt`, `sfx_plan`, …) |
| `label` | str | человеческое имя ноды |
| `sources[]` | list | документы, которые участвовали: `id`, `name`, `size` (байты), `kind` = `json`\|`text`, `rows` — сколько строк дал документ суммарно, `tables` — сколько таблиц |
| `tables[].id` | str | стабильный id: путь коллекции; при мультиисточнике — `<источник>.<путь>` |
| `tables[].title` | str | подпись для UI: имя коллекции + пометки о склейке/обрезке |
| `tables[].columns[].key` | str | ключ ячейки в `rows`, совпадает с путём поля (`fields.кадры`, `qc.verdict`) |
| `tables[].columns[].label` | str | подпись для шапки; по умолчанию = `key` |
| `tables[].columns[].type` | enum | `text` \| `number` \| `bool` \| `json` \| `long_text` |
| `tables[].rows` | list[dict] | строки; значения — str\|number\|bool |
| `tables[].total` | int | всего строк в коллекции (до лимита 5000) |
| `tables[].truncated` | bool | `true`, если строк было больше 5000 и отдано только 5000 |
| `params[]` | list | скаляры и служебные значения: `key`, `label`, `value` (**всегда строка**) |
| `warnings[]` | list[str] | короткие предупреждения для UI; не ошибки |

### 1.3. Типы колонок

| Тип | Когда | Как отдаётся |
|---|---|---|
| `number` | int/float (не bool) во всех непустых значениях колонки | число |
| `bool` | только true/false | bool |
| `json` | значение — массив объектов или объект (не разворачивается в колонку) | компактная JSON-строка |
| `long_text` | строка длиннее 300 символов | строка, в API обрезана до 2000 символов (`full=1` — целиком) |
| `text` | всё остальное (строки ≤300, смешанные типы, пустые) | строка |

Смешанный тип (числа + строки в одной колонке) → `text`, числа приводятся к строке.
Пустая колонка (все значения `null`) → `text`.

### 1.4. Коды ответа

| Код | Когда |
|---|---|
| 200 | всё ок; «нет документов» и «документ пуст» — это тоже 200 + `warnings` |
| 400 | документ существует, но не читается (нет файла по пути из meta, битый доступ) |
| 404 | ноды с таким `node_key` нет в графе проекта, либо `doc` не найден у ноды |

Важно (см. риски R5/R9): `n_topic`, `n_hero`, `n_backgrounds` существуют в `canvas_graph`, но у них
**ноль документов** — это 200 с пустыми `tables`/`params` и предупреждением, а **не** 404.

## 2. Документы ноды: что именно нормализуется

`GET /api/projects/{project_id}/node-llm/{node_key}/documents` → `{nodeKey, nodeType, label, llm, documents[]}`.

Документ (`documents[]`): `id`, `name`, `label`, `kind`, `path`, `size` (байты), `updatedAt`, `isJson`,
`exists`, `editable`, `field`.

`GET .../documents/<doc_id>` → тот же документ + `text` (полный текст), `chars`, `size` (байты UTF-8).
`doc_id` содержит `:` (`meta:shots.json`, `file:gpt_reply.txt`, `project:script_text`) — в URL кодировать
(`meta%3Ashots.json`).

Виды документов (`kind`):

| kind | Что это | Примеры |
|---|---|---|
| `file` | файл из папки ноды или из `meta`-путей ноды | `meta:shots.json`, `file:gpt_reply.txt` |
| `project_text` | текстовое поле проекта | `project:general_plan` (нода `plan`), `project:script_text` (нода `script`) |
| `meta_json` | JSON из `project.meta` | `meta:sfx_plan` (нода `sfx_plan`) |

Правила:
- **Флаг `isJson` не истина.** `meta:shots.json` → `isJson=true`, а `file:gpt_reply.txt` у `excel_gpt`-нод →
  `isJson=false`, хотя внутри валидный JSON. Тип документа определяется разбором текста, флаг — подсказкой.
- `size` в списке документов — размер файла в байтах; `chars`/`size` в ответе на чтение — по тексту.
- Дубликат `gpt_reply_raw.txt` при совпадении размера с `gpt_reply.txt` API уже скрывает — нормализатору
  делать нечего.
- `project_text` может быть пустым полем (`exists=false`) — тогда 0 таблиц + предупреждение.
- Документ 0 байт (встречается у `n_sfx_plan`) — валидный 200 с нулём таблиц + предупреждение.

## 3. Универсальные правила нормализатора

Правила намеренно не знают про конкретные ноды и русские ключи (кроме списка «ключей склейки» и эвристики
прозаических заголовков). Всё ниже — нормативный минимум; backend может добавить своё, но контракт раздела 1
и ожидания раздела 4 ломать нельзя.

### 3.1. Выбор коллекций

1. Разбираем текст как JSON. Получилось:
   - **корень — массив объектов** → одна таблица, id = `items` (или имя документа без расширения), все элементы строками.
   - **корень — массив примитивов** → не таблица: значение уезжает в `params` (имя — имя документа), UI покажет 0 таблиц.
   - **корень — объект** → идём по нему.
2. Объект: каждая пара `ключ → массив объектов` на пути длиной ≤2 от корня становится таблицей.
   Примеры: `{"сцены": [...]}` → таблица `сцены`; `{"qc": {"violations": [...]}}` → таблица `qc.violations`.
   Путь длиннее 2 — см. 3.5 (вложенные коллекции).
3. Массивы примитивов (`["c01","c02"]`, `["P1","P2"]`, `["R-VO-LONG S1-K1: …"]`) — **не таблицы**:
   в колонке родительской строки они склеиваются через `"; "` (тип `text`), на верхнем уровне объекта —
   уезжают в `params` (пустое значение → пустая строка, не пропускать).
4. Объекты, не содержащие массивов объектов (`counts`, `qc` со скалярами), не дают таблиц: их листья
   разворачиваются в `params` с ключом-путём (`counts.shots`, `qc.verdict`).
5. «Есть данные, но нет ни одной коллекции» — валидный случай: 0 таблиц, только `params`
   (`n_excel_gpt_pk_report` тому пример). UI обязан это показывать, а не «нет данных».
6. Пустые массивы объектов (`"issues": []`) — не таблица (0 строк не рисуем), значение уходит в `params`
   как `"[]"`/пусто. `warnings` не нужен.

### 3.2. Разворачивание вложенности в колонки

- Вложенный объект внутри элемента разворачивается в колонку `"путь.поле"` (`fields.кадры`,
  `qc.verdict`, `counts.shots`), до вложенности 4.
- Коллизия имён после разворачивания (`место` из двух разных объектов) → префикс именем родителя
  (`место` и `fields.место`), при полном совпадении пути — префикс именем массива (`кадры.место`).
- `null` → пустая строка в ячейке (не строка `"None"`, не `0`).
- Порядок колонок: порядок первого появления ключа в элементах; `id`/`номер`/`frame_uuid` — первыми.

### 3.3. Склейка массивов в одну строку (satellite-массивы)

Склеиваем только массивы **объектов**, которые относятся к одному и тому же ряду сущностей (кадры/сцены/шоты).

1. **По общему ключу.** Если у двух массивов одинаковая длина и есть хотя бы один общий ключ из набора
   `frame_uuid`, `кадр`, `id`, `shot_id`, `номер` — строки сопоставляются по значению этого ключа
   (первый найденный ключ из набора, порядок как в наборе). Несовпадение значения → строка с пустыми
   колонками второго массива + `warning`.
2. **По индексу.** Если общих ключей нет, но длины равны и оба массива «про кадры/сцены» — склейка по
   позиции (0-й с 0-м). Так устроен `n_excel_gpt_pk_shots`: `ops` (22) + `закадр_план` (22), общих ключей
   ноль, порядок совпадает (проверено: сцены 1…22 в обоих).
3. **Не склеиваем** массивы разной длины (`пункты` 24 и `сцены` 22 — остаются двумя таблицами; связь
   `сцены[].id_плана` показывает только ссылки, склейки по ней нет).
4. Колонки склеенной таблицы: префикс именем массива (`закадр_план.номер`, `закадр_план.закадр`),
   кроме случая, когда конфликта нет и префикс мешает читать (`frame_uuid` остаётся как есть).
   `id` таблицы — имя основного массива (`ops`), `title` помечает склейку.
5. Склеивать больше двух массивов можно, если ключ/длина совпадают у всех.

Фактически в проекте 2 склейка срабатывает **один раз**: `n_excel_gpt_pk_shots`, `ops` + `закадр_план` (22+22).
Больше равных длин с общим ключом/темой в проекте нет.

### 3.4. Проза → таблица блоков

Если `json.loads` упал и JSON-фрагмента нет (3.4.1), документ считается прозой:

- Таблица `blocks` (одна на документ), колонки: `заголовок` (`text`), `текст` (`long_text`), `тип` (`text`).
- Заголовок — строка, которая: короче/равна 120 символам, не пустая, не заканчивается на `. ! ? … , ; :`,
  не содержит `". "` (не предложение). Так ловятся `Пролог`, `Глава I`…`Глава V`,
  `Картинка для привлечения внимания`, `"Cыны Империума"`.
- Блок = заголовок + все строки до следующего заголовка. Текст до первого заголовка — отдельный блок
  с пустым `заголовок` и `тип = "вступление"`; блоки с заголовком — `тип = "раздел"`.
- Соседние заголовки без текста между ними дают блоки с пустым `текст` (не склеивать, не выбрасывать —
  иначе поедут ожидаемые числа 4.1).
- `params`: `key = "исходный_текст"`, `value` = весь текст, максимум **20000** символов (дальше обрезка),
  `label = "Исходный текст (обрезка)"` при обрезке.
- Ячейки `текст` — `long_text`; в API обрезка 2000 (раздел 3.6), `full=1` — целиком.

Ожидаемые числа для проекта 2 (эвристика выше): `n_plan` — **9 блоков** (вступление + 8 заголовков),
`n_script_1794875142991` — **6 блоков** (вступление + Глава I…V). Допуск: 8–10 и 5–7, если backend
склеивает соседние заголовки или иначе трактует вступление.

### 3.4.1. JSON-фрагмент в прозе (для `n_excel_gpt_pk_cast`)

Порядок разбора документа:

1. `json.loads(text)` целиком.
2. Упало → ищем **первый сбалансированный `{…}`** с учётом строковых литералов, кавычек и экранирования
   (не регуляркой!). Разбираем найденный фрагмент.
3. Фрагмент разобрался → работаем как с JSON-объектом, плюс:
   - `params` `{key:"преамбула", label:"Проза до JSON", value: <текст до `{`, обрезка 2000>}`;
   - `warnings`: `"json.loads упал на прозе; разобран JSON-фрагмент с символа 196"`.
4. Фрагмент не найден/не разобрался → обычная проза (3.4).
5. Префикс короче ~50 символов, заканчивается `:`/`.` — это служебная фраза модели; всё равно кладём в
   `params`, но `warnings` не нужен (шум в UI). Фактически у `cast` префикс 196 символов — предупреждение уместно.

### 3.5. Вложенные коллекции (массивы объектов внутри элементов) — расширение глубины 4

Основной минимум (3.1) даёт таблицы только на пути ≤2. Если backend реализует полноценную глубину 4
(см. «Открытые вопросы»), правило такое:

- Массив объектов внутри элемента коллекции становится **отдельной таблицей** с id = путь
  (`ops.fields.кадры`, `сцены.violations`), а не JSON-ячейкой.
- В строку переносится ссылка на родителя: первая из колонок `id`, `frame_uuid`, `номер` родителя,
  имя колонки — `<родитель>.<ключ>` (`frame_uuid` у `ops`, `номер` у `сцены`).
- Вложенный массив **не** разворачивается, если он пуст во всех элементах (0 строк → в `params`).
- Строки таких таблиц — плоские: вложенные массивы примитивов внутри них склеиваются через `"; "`.
- Лимит 5000 строк и `truncated` действуют на каждую таблицу отдельно.

Без этого расширения (минимальный путь) эти массивы остаются колонкой типа `json` в строке родителя —
данные не теряются, но UI получает тяжёлую ячейку (раздел 7, R2).

### 3.6. Лимиты и обрезка

| Ограничение | Значение | Поведение |
|---|---|---|
| Глубина обхода контейнеров | 4 | глубже — значение целиком в `json`-ячейку |
| Строк в одной таблице | 5000 | `rows` = 5000, `total` = фактическое, `truncated = true`, `warnings` += `"таблица …: показано 5000 из N"` |
| Строка → `long_text` | > 300 символов | тип колонки `long_text` |
| Обрезка `long_text` в API | 2000 символов | в ответе `…`; `?full=1` — полное значение |
| `params.value` | 2000 символов | обрезка с `…` |
| `params` прозы (`исходный_текст`) | 20000 символов | обрезка, в `label` — пометка |
| Таймаут нормализации | ~3 с | при превышении — 200 с пустыми таблицами и `warnings`, не 500 |
| Таблиц на документ | без жёсткого лимита | фактический максимум в проекте 2 — 3 |

Обрезка **не** применяется к `number`/`bool`/`json`-ячейкам по 2000 — но `json`-ячейка всё равно должна
отдаваться компактно (`json.dumps(..., ensure_ascii=False, separators=(",",":"))`).
`warnings` не дублируют друг друга и не заменяют данные.

### 3.7. `params`: что туда попадает

1. Все скаляры корня и объектов, не ставших таблицами: ключ = путь (`counts.shots`, `qc.verdict`).
2. Массивы примитивов: верхнеуровневые — `key = имя`, `value = "; ".join(...)` (обрезка 2000);
   внутри строки таблицы — колонка `text` с той же склейкой.
3. Пустые массивы/объекты: `value = ""` или `"[]"` (решить один раз и держать), не выбрасывать молча —
   verifier сверяет состав.
4. Прозовые документы: `исходный_текст`; `cast`: `преамбула`.
5. При мультиисточнике одинаковый `key` из разных документов → префикс именем документа (`gpt_reply.qc.verdict`).

`label` по умолчанию = `key`; для известных ключей можно человекочитаемый (`Секунд`, `Тип`), это не влияет на приёмку.

### 3.8. `sources` и `warnings`

- `sources` — все документы ноды, включая те, что дали 0 таблиц (иначе не видно, что документ вообще был).
  `kind`: `json`, если текст разобрался как JSON (целиком или фрагментом), иначе `text`.
- `rows` в `sources` — сколько строк дал этот документ по всем его таблицам (для прозы — число блоков).
- `warnings` — короткие строки, без стека и без путей на диске:
  - `"нет документов ответа ЛЛМ для ноды <node_key>"`;
  - `"документ пуст: <name>"`;
  - `"json.loads упал на прозе; разобран JSON-фрагмент с символа <N>"`;
  - `"таблица <id>: показано 5000 из <N>"`;
  - `"long_text обрезан до 2000 символов (?full=1 — целиком)"` — одной строкой на ответ.

## 5. Исключения

### 5.1. `n_excel_gpt_pk_cast` — проза + JSON-фрагмент, `json.loads` падает

Факт (`file:gpt_reply.txt`, 9015 б / 5415 симв.):

- первые **196 символов** — служебная русская фраза модели, заканчивается точкой:
  `«Собираю реестр по первому появлению: отделяю реально действующих людей от толпы, упоминаний и
  изображённых на документе фигур; смену гражданской одежды Аделфуса на форму учту как видимую вариацию.»`
- дальше — валидный JSON-объект `{"персонажи": [ … ]}` ровно **5219 символов**, 11 персонажей
  (c01–c11), ключи персонажа: `id`, `имя`, `внешность`, `одежда`, `характер`, `правила`, `voice_prompt`.
- `json.loads(весь текст)` → `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`.
- `isJson` в списке документов = `false` (это `.txt`), так что по флагу тоже не угадать.

Как обходиться: раздел 3.4.1 — сбалансированный первый `{…}` + разбор фрагмента. Никаких «удалить первую
строку» (в других нодах префикс может быть в несколько строк или отсутствовать), никаких регулярных
выражений на вложенные фигурные скобки.

Ожидание: 1 таблица `персонажи` **11 строк**, `params.преамбула` = 196 символов, `warnings` про фрагмент.
Если этого не сделано — verifier увидит прозовые блоки (или 0 таблиц) вместо реестра персонажей: это
блокирующий дефект, потому что реестр персонажей — самый простой для чтения результат.

### 5.2. Два документа одной ноды с одинаковыми именами коллекций

- `n_excel_gpt_pk_scenes`: массив `сцены` есть и в `plan_scenes.json` (22), и в `gpt_reply.txt` (22).
- `n_excel_gpt_pk_shots`: массив `ops` есть в `shots.json` (22) и в `gpt_reply.txt` (1).

Без префикса источника таблицы с одинаковым `id` склеятся/потеряются, а UI не покажет, откуда строка.
Требование: при мультиисточнике `tables[].id` = `<имя_источника>.<путь>` (`plan_scenes.сцены`,
`gpt_reply.сцены`), `sources[].id` — id документа. Внутри одного документа суффикс не нужен.

### 5.3. `n_excel_gpt_pk_report` — данные есть, таблиц нет

`report.json` — 5 скаляров (`отчёт` — путь к `reports/shots-report.html`, `сцен` 22, `кадров` 129,
`персонажей` 11, `фонов` 21). Коллекций нет → 0 таблиц, 5 params. UI не должен писать «Нет
структурированных данных», если `params` непусты.

### 5.4. Вложенные массивы внутри строк (`ops[].fields.кадры`, `сцены[].violations`)

Один `op` = мастер-кадр со своим `frame_uuid`, внутри `fields.кадры` — 4–11 кадров (всего по документу 123,
первый `S1-K1`, последний `S22-K1`, `parent_id` у всех `null`). У `qc_report` в каждой сцене до 6 нарушений.
Правило раздела 3.5 (или `json`-ячейка без него). Не пытаться «развернуть кадры в колонки» — 30 ключей
и массивы внутри, получится мусор из `кадры[0].id`, `кадры[1].id`, …; сравнение по глубине 4 — да,
по индексу элемента массива — нет.

### 5.5. Пустой документ у `n_sfx_plan`

`file:gpt_reply.txt`, 0 байт, `chars=0`, `json.loads("")` падает. Не 500 и не 400: 200 + `warnings`
`"документ пуст: gpt_reply.txt"`, 0 таблиц.

### 5.6. Ноды без документов (`n_topic`, `n_hero`, `n_backgrounds`)

`llm=false`, `documents=[]` — это не ЛЛМ-ноды с ответом: тема живёт в `project.topic`
(«ролик в стиле вархамер история ереси хоруса»), персонажи и фоны — в файлах групп
(`data/videos/pavypvya/characters/c01.json … c11.json`, `backgrounds/f01 …`) и в других нодах
(`n_excel_gpt_pk_cast`, `n_excel_gpt_pk_backgrounds`). Что отдаёт `/table`: 200, `sources=[]`,
`tables=[]`, `params=[]`, `warnings=["нет документов ответа ЛЛМ для ноды n_topic"]`.
Возвращать 404 нельзя — нода есть в графе, frontend откроет вкладку и покажет предупреждение.

## 6. Неожиданные форматы, которые нашлись по факту

1. **`cast`:** JSON начинается с 196-го символа после прозы (5.1). `json.loads` падает, флаг `isJson=false`.
2. **`gpt_reply.txt` у `excel_gpt`-нод** — у большинства валидный JSON (skeleton, dialogues, backgrounds,
   qc, shots), но `isJson=false` и `kind=file`; исключение — `cast` (см. 5.1). Размер 500 б…28 КБ.
   Определять JSON только разбором.
3. **`n_plan` и `n_script`** — не файлы, а поля проекта (`general_plan`, `script_text`), `kind=project_text`,
   `path=null`. Огромные (14–26 КБ) куски чистого повествования без структуры.
4. **`shots.json` — 594 792 байта / 360 760 символов:** `ops` 22 + `закадр_план` 22 + 5 скаляров;
   внутри `ops` спрятаны 123 кадра. Самый тяжёлый документ проекта.
5. **Вложенные массивы с массивами внутри** (`ops[].fields.кадры[].предметы` — массив примитивов,
   у большинства пустой).
6. **`qc_report.json`:** вложенные `violations` (объекты, 65 шт. суммарно), `fixes` (строки, 65),
   `issues` (всегда пустой). Вердикты: pass 1, fail 20, warn 1.
7. **`style_report.json`:** `counts` — объект из 5 чисел, `проблемы` — массив 12 строк
   (`"R-VO-LONG S1-K1: кусок 107 символов > 80"`), `style_file` — абсолютный Windows-путь в значении.
8. **`dialogues`:** всего 3 реплики и скаляр `тип="диалог"`; документ 521 байт — проверка «маленький JSON».
9. **Документы одной цепочки не согласованы по числам:** `style_report.json` и `report.json` говорят
   `кадров 129`, а `shots.json` даёт **123** кадра в 22 ops. Разница точечная: у сцен 1, 10, 15 в
   `style_report.json` на 3, 1 и 2 кадра больше, чем в текущем `shots.json` (7/4, 12/11, 12/10) —
   это разные снимки состояния цепочки, а не ошибка нормализатора. Аналогично `report.json` говорит
   `фонов 21`, `backgrounds`-нода — **19** фонов. Поэтому ожидаемые строки в разделе 4
   взяты из документов ноды, а не из отчётов. Verifier не должен «сверять с отчётом» и падать на этом.
10. **`plan_scenes.json`:** массив `пункты` (24) ≠ `сцены` (22), связь — `сцены[].id_плана` (`["P1","P2"]`),
    то есть ссылочная, не позиционная. Склейки нет (3.3.3). Плюс скаляр `план_с_номерами` (14 470 симв.) —
    это тот же текст плана, что в `n_plan`, только с номерами.
11. **`n_sfx_plan`** — ЛЛМ-нода с пустым документом (5.5).

### 8.3. Автопроверка ожиданий раздела 4

Один прогон по всем 14 нодам, печатает PASS/FAIL по мультимножеству строк (не зависит от префиксов id):

```python
import json, urllib.request, urllib.parse

BASE = "http://127.0.0.1:8766"
EXPECT = {
    "n_topic": [],
    "n_plan": [9],                      # допуск 8..10
    "n_script_1794875142991": [6],      # допуск 5..7
    "n_hero": [],
    "n_backgrounds": [],
    "n_excel_gpt_pk_scenes": [22, 22, 24],
    "n_excel_gpt_pk_cast": [11],
    "n_excel_gpt_pk_skeleton": [22],
    "n_excel_gpt_pk_dialogues": [3],
    "n_excel_gpt_pk_backgrounds": [19],
    "n_excel_gpt_pk_shots": [1, 22],
    "n_excel_gpt_pk_qc": [1, 22],
    "n_excel_gpt_pk_style": [22],
    "n_excel_gpt_pk_report": [],
}
TOLERANCE = {"n_plan": (8, 10), "n_script_1794875142991": (5, 7)}

for node, expected in EXPECT.items():
    try:
        data = json.load(urllib.request.urlopen(f"{BASE}/api/projects/2/node-llm/{node}/table", timeout=60))
    except Exception as exc:
        print(f"FAIL {node}: {type(exc).__name__}: {exc}")
        continue
    got = sorted(len(t["rows"]) for t in data.get("tables") or [])
    if node in TOLERANCE:
        lo, hi = TOLERANCE[node]
        ok = len(got) == 1 and lo <= got[0] <= hi
    else:
        ok = got == expected
    print(("PASS" if ok else "FAIL"), node, "rows=", got, "expected=", expected, "params=", len(data.get("params") or []))
```

### 8.4. Снятие фактов заново (повторить инвентаризацию)

```python
import json, urllib.request, urllib.parse
BASE = "http://127.0.0.1:8766"
NODES = ["n_topic","n_plan","n_script_1794875142991","n_hero","n_backgrounds",
         "n_excel_gpt_pk_scenes","n_excel_gpt_pk_cast","n_excel_gpt_pk_skeleton",

         "n_excel_gpt_pk_qc","n_excel_gpt_pk_style","n_excel_gpt_pk_report"]
for node in NODES:
    docs = json.load(urllib.request.urlopen(f"{BASE}/api/projects/2/node-llm/{node}/documents", timeout=60))
    print(node, docs["nodeType"], [(d["id"], d["size"]) for d in docs["documents"]])
    for d in docs["documents"]:
        url = f"{BASE}/api/projects/2/node-llm/{node}/documents/{urllib.parse.quote(d['id'], safe='')}"
        text = json.load(urllib.request.urlopen(url, timeout=60))["text"]
        try:
            root = json.loads(text)
            print("   ", d["name"], "JSON", type(root).__name__, list(root)[:5] if isinstance(root, dict) else len(root))
        except ValueError as exc:
            print("   ", d["name"], "NOT JSON", str(exc)[:80])
```
